# Code review: paper-odca-des simulator (2026-09-19)

Read-only review of `code/odca/`, `config.py`, the runners, `aggregate_multiseed.py`, `golden.py`
and the figure scripts. No simulation was run. The only timings below come from a few-second
micro-benchmark of single primitives (`find_blockage`, property lookups, `rng.random()`, SimPy
event creation) on the loaded machine, plus the counters and wall times already in
`code/output/` from the current rerun. Items N2-N8 in HANDOVER.md are not repeated.

Legend for the last column: **neutral** = the golden fingerprint should match exactly;
**moves numbers** = changes results, needs a decision and a rerun; **golden decides** = probably
neutral, but event ordering at equal timestamps could shift, so only the golden run can tell.

Important limit on the proof: `golden.py:25-44` fingerprints only `summary_statistics` and the
counters. It does **not** cover `fd_data` (Edie, passage-time), the demand sweep, the incident
run or any figure script. A change to `metrics.py` Edie code or to those scripts is unproven by
the golden check and needs its own before/after diff of the JSON.

## Top 10, ranked

1. **Segment-end trips get destination lane = entry lane** (`generator.py:89-94`, `engine.py:166`, `vehicle.py:754-758`). The paper says segment-end vehicles "exit from their current lane" (tex:874). The code pulls every through vehicle that has drifted back to its entry lane (MLC p about 0.65 per evaluation by 75% of the trip). In the bottleneck, one third of demand has destination lane 3, which is closed from cell 300 to the end, so those vehicles cannot ever meet `_at_destination`, get pulled back into lane 3 upstream of the drop, then pushed out again. Evidence in the outputs: S1 4.9 lane changes/km (about 25 per vehicle), BN 1.6-2.5/km (7-11 per vehicle on 4.5 km). Moves numbers.
2. **"Throughput" is not what the paper defines, and the right-censoring grows with travel time** (`metrics.py:202-206, 232`). Code: vehicles that entered after warm-up and finished before the end. Paper (tex:973): vehicles exiting during the measurement period. Vehicles that enter in the last travel-time window are dropped: about TT/(T-W), so about 5-11% low in S1 (TT 376 s over 3300 s), up to about 20% in BN (TT 400 s over 1680 s), and less for AV scenarios, which inflates the AV gains. Also, time spent queued at the origin is excluded from travel time and delay (`vehicle.py:177-188` stamps `time_entered` on seizing the origin cell): in S1 about 1,750 of 7,000 generated vehicles are still waiting at the origin at t=3600 (log: 7,000 generated, 4,600 completed, 650 in network). Moves numbers.
3. **Vehicles become invisible while crossing a cell slowly** (`vehicle.py:164-171, 330-355`). The old cell is released and its `.vehicle` cleared tau after the next cell is *acquired*, but the vehicle only registers in the new cell after the traversal. When traversal > tau (HDV below 0.67 cells/s, AV tau 0.5 below 2.0 cells/s, which covers most congested AV movement) the vehicle is on no cell for (1/v - tau) s. `find_leader`, `find_follower`, LC safety and neighbour wake-ups all miss it, and a follower can register in the old cell while `self.cell` still points there (two vehicles in one cell in the decision state and in Edie segments). Contradicts ARCHITECTURE invariant 2 ("released tau after its vehicle leaves it"). Moves numbers.
4. **LC safety check ignores the target cell's own occupant** (`vehicle.py:485-486` with `cell.py:108-128`, both scans start one cell beyond the target). A lateral request to an occupied cell passes the check, the vehicle then stops in its own lane for up to `_LC_PATIENCE` = 3 s (`vehicle.py:313`), and because `_get_target_cell` already set `last_lc_time` and `count_lane_changes` (`vehicle.py:443-444, 453-454`), the 10 s cooldown then suppresses destination MLC after a *failed* attempt. Add `target.vehicle is None and not target.resource.users` to the check; count completions, not attempts. Moves numbers.
5. **Missed off-ramp exits are silent and teleport** (`vehicle.py:223-229, 243-249`). `_at_destination` uses `idx >= dest - 1`, so a vehicle that misses ramp 300 in lane 2 exits at whatever later cell it first reaches lane 1 (for example cell 421, where there is no ramp), or at the network end via the end-of-lane rule. No counter exists, so nobody knows how often. Add a `missed_exits` counter (neutral for existing keys), then decide the policy (moves numbers).
6. **Lane-change probabilities are per evaluation, so the LC hazard depends on how often a vehicle is evaluated** (`vehicle.py:697, 711, 738, 748`; `av_controller.py:54-55`). AVs are evaluated at 10 Hz, HDVs at about 1 Hz plus wake-ups, so an AV with the same MLC p has about 10 times the per-second hazard. The action-interval sensitivity result (tex:1118-1120, "closer to continuous Newell") therefore also changes the LC rate. Convert to a rate: `p_eval = 1 - (1 - p)**(dt / dt_ref)`. Moves numbers; at minimum, state it in the paper.
7. **The aggregator can silently produce n=19 or n=21** (`aggregate_multiseed.py:52-59, 91`). An unreadable JSON (a run killed mid-write during this rerun) is printed and skipped; a seed run twice in two batch dirs is counted twice. Nothing checks n == 20 or unique (label, seed, ai). Add both asserts. Neutral.
8. **Quoted counts measure something other than what the text says** (`run_scalability.py:73-78`, `vehicle.py:635, 664`). "Total events" (tex:1157) is lane changes + slowdowns + CF evaluations + controller ticks; the dominant work (cell moves, releases, timeouts) is not in it, which is why wall time grows 9.3x (80 to 750 s) for 16x cells while "events" grow 4.9x. "CF evaluations" (tex:1197, "3x fewer than a time-stepped model") excludes free-flow evaluations. The demand sweep inflow is a Poisson stream at k·v_max (`run_demand_sweep.py:129-130`), not the "inflow that replaces exiting vehicles" of tex:902; at k=0.8 on 4 lanes it generates about 20,000 vehicles that mostly wait at the origin. Record SimPy's own event count after `env.run` (neutral) and fix the text or the code.
9. **Neutral runtime bundle, roughly 10-15% per run**: a per-lane blockage index so `find_blockage` is O(1) (it walks 30-36 cells 2-4 times per evaluation even in S1-S4, which have no blocked cell: about 1.1 µs per call, about 20-30 s per S3 run); compute the blockage distance once per evaluation instead of twice; precompute static neighbour links on `Cell` (notify lists cost about 1.5 µs to build, twice per move, about 15 s per run); prune finished AVs from `AVController._vehicles` keeping order (138 µs per tick at 2,500 AVs, about 5 s per S4 run); delete the unread passage-time `fd_data`; run the S1 figure simulation once in `generate_paper_figures.py`. The bulk of the runtime is SimPy machinery per cell move; profile a `--quick` golden run before investing more.
10. **Trajectory memory: 192 bytes per record** (`vehicle.py:41-47, 809-818`, measured). About 3-3.8 million records per S1-S4 run is 0.55-0.75 GB per process; the 3,200-cell scalability run is about 6 million records, 1.2 GB. Columnar `array('d')/array('H')/array('B')` storage per vehicle is about 25 bytes per record (8x less) and bit-identical in value; it is a core-type change (`TrajectoryRecord`), so it goes through /architect. The incident JSON (104 MB, list of dicts) is loaded twice per file by `generate_figures.py:562-563, 632-633`.

Just outside the ten: the lateral grant race (row A10), which is unreachable today only because tau <= 3.0 = patience.
